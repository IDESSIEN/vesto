2. Smart Contract: VestoEscrow.sol

The contract is intentionally minimal. It does one thing: hold USDC in escrow against a registered invoice ID and release it to the correct party on instruction. No upgradability, no admin withdrawal path, no oracle dependency.

2.3 Key Functions

FunctionCallerDescription
registerInvoice(bytes32 id, address seller, uint256 amount)Admin onlyPre-registers invoice before marketplace listing. Prevents ID squatting.
fundInvoice(bytes32 id)Lender (any)Lender approves USDC then calls. Transfers advance amount from lender to escrow. Sets invoice state to funded.
markRepaid(bytes32 id)Admin onlyCalled after admin confirms buyer payment. Moves funds from escrow to seller's pendingClaims.
claimPayout()Seller (any)Pull-pattern: seller claims their accumulated pendingClaims. Uses ReentrancyGuard.
resolveDispute(bytes32 id, bool refundLender)Admin onlyOn dispute: either refunds lender or pays seller from escrow.
pendingClaims(address)ViewReturns outstanding claimable USDC for an address.

2.5 Security Model

ThreatMitigation
Re-entrancy on claimPayoutReentrancyGuard nonReentrant modifier. Balance zeroed before transfer (checks-effects-interactions).
USDC blocklist bricking lenderPull-claim pattern. Lender initiates withdrawal. Admin cannot force-push to a blocked address.
Admin confiscationadminReroute function removed in audit. Admin can only: register, mark repaid, resolve dispute.
Invoice ID squattingAdmin pre-registration required before any lender can fund. Invoice ID is a bytes32 hash.
Integer overflowSolidity 0.8+ built-in overflow protection. SafeERC20 for all token transfers.
Double-fundState machine check: invoice must be in state 0 (registered) to accept funding.

4. Application State (V1)

All application state lives in src/context/AppContext.tsx. This is a deliberate V1 simplification — no database calls, instant UX, zero infrastructure dependency. Every piece of state is replaced by a Supabase query in V2.

State shape

seller: SellerProfile // current seller session
lender: LenderProfile // current lender session
admin: AdminProfile // current admin session
invoices: Invoice[] // all invoices (shared across roles)
verificationQueue: VerificationRequest[]
sellers: Record<string, SellerProfile> // admin KYC approval affects this map
sellerView: string // current seller screen
lenderView: string // current lender screen
adminView: string // current admin screen
role: UserRole | null // 'seller' | 'lender' | 'admin' | null
selectedBatchIds: string[] // batch funding selection

6. Off-Chain Backend (Supabase — V2)

The full schema is in the Backend Schema document. This section covers the integration architecture.

6.1 Data Boundary

What lives onchainWhat lives in Supabase
USDC balances and escrow fundsSeller and lender profiles
Invoice funding state (registered/funded/repaid)Invoice metadata, buyer details, document URLs
Pending claim amounts per addressKYC documents and verification status
All transaction hashes and eventsAdmin notes, dispute records, analytics aggregates

6.2 Sync Pattern

Arc events (InvoiceFunded, PayoutClaimed, DisputeResolved) are listened to by a Supabase Edge Function webhook. The function writes the event to the corresponding Supabase table, keeping off-chain state consistent with onchain reality without requiring the frontend to poll.

7. Technical Evolution Path

V2 (3–9 months)

  • Supabase wiring: Replace React context mock state with real Supabase queries. Auth via Supabase Auth (email OTP for sellers, wallet-sign for lenders).
  • KYC API: Integrate Smile Identity (Africa) or Onfido (global) for automated document verification. Webhook confirms to Supabase, which triggers admin queue entry.
  • CCTP bridging: Allow lenders to fund invoices from Base, Arbitrum, or Polygon USDC via Circle CCTP. Frontend: use @circle-fin/bridge-kit.
  • Lender pool contracts: Deploy VestoPool.sol — ERC-4626-style vault accepting USDC deposits from multiple lenders, allocating to invoices on a risk-weighted basis.
  • Contract verification: Verify VestoEscrow.sol source on Arc explorer via Foundry forge verify-contract.

V3 (9–18 months)

  • Tokenised invoices: Each funded invoice mints an ERC-1155 token representing the lender's position. Enables secondary-market trading.
  • On-chain credit scoring: Attest seller repayment history as a Soul-Bound Token (ERC-5192). Score improves advance rate and credit limit automatically.
  • Governance: VESTO governance token for protocol parameter voting (advance rates, fee tiers, pool allocation weights).
  • Cross-chain identity: ERC-8004 agent identity registry for automated lender agents that fund invoices programmatically.
