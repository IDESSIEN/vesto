01

The three-layer model

Think of your app as a restaurant. This mental model explains every decision in this guide.

The dining room — your React frontend

This is what users see and click. It runs entirely inside the user's browser. Anyone in the world can open DevTools and read every line of code and every network request. It should contain zero secrets — no private API keys, no passwords, no admin tokens. It talks to the kitchen by making HTTP requests.

The kitchen — your Supabase Edge Functions

This is where the real work happens. Users never see inside it. It holds all the secrets and validates every request before acting on it. Your five Edge Functions live here: send-acknowledgement, handle-acknowledgement, payment-received, process-settlements, send-reminders.

The pantry — Supabase secrets and Netlify env vars

This is where keys are stored at runtime. The code reads them with Deno.env.get('KEY_NAME') in Edge Functions and import.meta.env.VITE_KEY in the browser — but only the safe anon key goes in the browser. The real secrets never leave the pantry.

The one rule Secret keys never go in the browser. If a variable name starts with VITE_, it is bundled into the browser build and is visible to anyone. Only two variables should ever have the VITE_ prefix: VITE_SUPABASE_URL and VITE_SUPABASE_ANON_KEY. Everything else is server-side only.
02

Every key Vesto uses

Here is the complete map of every credential the app depends on, where it lives, and whether it is safe to expose.

Key name What it does Lives in Safe to expose?
VITE_SUPABASE_URL The address of your Supabase project .env + Netlify env vars Yes
VITE_SUPABASE_ANON_KEY Lets the browser talk to Supabase with RLS enforced .env + Netlify env vars Yes — RLS is the lock
SUPABASE_SERVICE_ROLE_KEY Full database access — bypasses all RLS Supabase Edge Function secrets ONLY Never in browser
EMAIL_API_KEY Sends emails via Resend or SendGrid Supabase Edge Function secrets ONLY Never in browser
BAAS_WEBHOOK_SECRET Validates incoming payment webhooks from BaaS provider Supabase Edge Function secrets ONLY Never in browser
Why is the anon key safe to expose? The anon key is more like a door handle than a key. The real lock is Row Level Security (RLS). When a user logs in, Supabase gives them a JWT token. Every database request carries that token. Supabase checks the token against RLS rules before returning any data. Even if someone steals the anon key, they can only see what an unauthenticated user is allowed to see — which in Vesto is nothing.
03

Create your Supabase project

1
Go to supabase.com and sign in
Create a free account if you don't have one. The free tier supports up to 500MB database and 2GB bandwidth — sufficient for early-stage testing.
2
Create a new project
Click "New project". Choose a name (e.g. vesto-production), set a strong database password, and select the region closest to your primary user base (for East Africa: eu-west-1 or ap-southeast-1).
Save your database password somewhere safe. You will need it for the Supabase CLI later. Supabase does not show it again.
3
Copy your Project URL and Anon Key
Go to Project Settings → API. You will see two values:
# Project URL — looks like this:
VITE_SUPABASE_URL=https://abcdefghijklmnop.supabase.co

# Anon / Public Key — a long JWT string starting with eyJ:
VITE_SUPABASE_ANON_KEY=eyJhbGciOiJIUzI1NiIsInR5cCI6IkpXVCJ9...
Copy both values. You will paste them into your .env file and Netlify in the next two steps.
4
Copy your Service Role Key — but keep it safe
On the same API settings page, scroll down to find the Service Role Key. Copy it but do NOT paste it into your .env file. This key bypasses all RLS. It goes only into Supabase Edge Function secrets (Section 05).
5
Create your .env file
In your project root, copy .env.example to .env and fill in exactly two values:
# .env — this file never gets committed to GitHub
VITE_SUPABASE_URL=https://YOUR_PROJECT_REF.supabase.co
VITE_SUPABASE_ANON_KEY=YOUR_ANON_KEY_HERE
The .env file is in .gitignore and must never be committed to GitHub. If it ever is committed, rotate both keys immediately from the Supabase dashboard.
04

Set environment variables on Netlify

Your .env file is for local development only. Netlify needs the same two values set in its dashboard so the deployed build can connect to Supabase.

1
Open your Netlify site settings
Go to app.netlify.com → your site (clever-alpaca-c23dbf) → Site configuration → Environment variables.
2
Add the two safe variables
Click "Add a variable" for each:
VITE_SUPABASE_URL      = https://YOUR_PROJECT_REF.supabase.co
VITE_SUPABASE_ANON_KEY = eyJhbGci...
Set scope to "All scopes" (production + deploy previews + branch deploys).
3
Trigger a new deploy
Go to Deploys → Trigger deploy → Deploy site. Netlify injects env vars at build time — they only take effect after a fresh build, not on page refresh.
Why only two variables on Netlify? Netlify environment variables are injected into the browser bundle at build time. Any variable you set here becomes readable by anyone who inspects your site. Only the two VITE_ prefixed variables belong here. The service role key, email key, and webhook secret go into Supabase Edge Function secrets — they never touch Netlify.
05

Set secrets in Supabase Edge Functions

Edge Functions run on Supabase's servers, not in the browser. Their secrets are stored encrypted in Supabase's infrastructure and are only accessible to the functions themselves at runtime.

1
Navigate to Edge Function secrets
In your Supabase project → Edge Functions → Manage secrets. This is separate from the API settings page.
2
Add all five secrets
SUPABASE_SERVICE_ROLE_KEY = eyJhbGci...   # from Project Settings → API
EMAIL_API_KEY             = re_xxxx...    # from Resend dashboard (see Section 08)
BAAS_WEBHOOK_SECRET       = whsec_xxxx.. # from your BaaS provider dashboard
EMAIL_FROM_ADDRESS        = noreply@vesto.finance
APP_URL                   = https://clever-alpaca-c23dbf.netlify.app
3
Understand how functions read secrets
Inside any Edge Function, secrets are read like this — they are never hard-coded:
// ✅ Correct — reads from the encrypted secrets store
const apiKey = Deno.env.get('EMAIL_API_KEY');

// ❌ Wrong — never write a key directly in code
const apiKey = 're_real_key_here'; // this gets committed to GitHub
Supabase automatically injects SUPABASE_URL and SUPABASE_ANON_KEY You do not need to add these two to secrets — Supabase injects them automatically into every Edge Function. Only add values that are not already provided by the platform.
06

Run the database migrations

Migrations create all your tables, RLS policies, triggers, and security rules. They must be run in order — each one builds on the previous.

# File What it creates
1 20260905000000_initial_schema.sql Core tables (profiles, documents, invoices, verifications, admin_notes), RLS policies, is_admin() helper
2 20260923000000_hybrid_settlement.sql Settlement tables (invoice_virtual_accounts, invoice_settlements, pending_settlements), settlement RLS
3 20260923000001_hybrid_settlement.sql Additional settlement columns on invoices (grace_period_days, final_repayment_deadline, deadline_locked)
4 20260924000000_buyer_registry.sql Buyers table with credit scoring fields, concentration risk view
5 20260924000000_buyer_acknowledgements.sql Buyer acknowledgements table, HMAC token fields, audit log
6 20260925000000_security_hardening.sql Column-level protection triggers, admin-only RPC functions, immutability guards
1
Open the Supabase SQL Editor
Go to your Supabase project → SQL Editor → + New query.
2
Run each migration file in order
Open each file from your project's supabase/migrations/ folder, copy the entire contents, paste into the SQL Editor, and click Run. Wait for "Success" before running the next file.
# The files are in your project at:
supabase/migrations/20260905000000_initial_schema.sql
supabase/migrations/20260923000000_hybrid_settlement.sql
supabase/migrations/20260923000001_hybrid_settlement.sql
supabase/migrations/20260924000000_buyer_registry.sql
supabase/migrations/20260924000000_buyer_acknowledgements.sql
supabase/migrations/20260925000000_security_hardening.sql
3
Verify RLS is enabled on every table
Go to Table Editor. Click each table and look for the orange "RLS enabled" badge in the top right. Every table must show this badge. If any table shows "RLS disabled", run this in the SQL Editor:
ALTER TABLE public.your_table_name ENABLE ROW LEVEL SECURITY;
4
Set up the pg_cron job for process-settlements
The settlement processor runs every 15 minutes. Enable it with this SQL:
-- Enable pg_cron extension (run once)
CREATE EXTENSION IF NOT EXISTS pg_cron;

-- Schedule process-settlements every 15 minutes
SELECT cron.schedule(
  'process-settlements',
  '*/15 * * * *',
  $$
    SELECT net.http_post(
      url := current_setting('app.supabase_url') || '/functions/v1/process-settlements',
      headers := jsonb_build_object(
        'Authorization', 'Bearer ' || current_setting('app.service_role_key'),
        'Content-Type', 'application/json'
      ),
      body := '{}'::jsonb
    );
  $$
);
07

Deploy the Edge Functions

Edge Functions are deployed using the Supabase CLI from your local machine or CI pipeline.

1
Install the Supabase CLI
# macOS
brew install supabase/tap/supabase

# Windows / Linux
npm install -g supabase
2
Log in and link your project
supabase login
# Opens browser — log in with your Supabase account

supabase link --project-ref YOUR_PROJECT_REF
# YOUR_PROJECT_REF is the part before .supabase.co in your project URL
# e.g. if URL is https://abcdefgh.supabase.co → ref is abcdefgh
3
Deploy all five functions
supabase functions deploy send-acknowledgement
supabase functions deploy handle-acknowledgement
supabase functions deploy payment-received
supabase functions deploy process-settlements
supabase functions deploy send-reminders
Each function takes about 30 seconds. You will see "Deployed Function" for each one. The function URLs follow the pattern:
https://YOUR_PROJECT_REF.supabase.co/functions/v1/FUNCTION_NAME
4
Delete the legacy Agora function
The agora/index.ts function is a leftover from the original app and is not used in Vesto. Delete it to avoid unnecessary invocations:
supabase functions delete agora
08

Wire the email provider

Vesto sends two types of emails: buyer acknowledgement requests and seller repayment reminders. Both use the EMAIL_API_KEY secret you set in Section 05.

1
Create a free Resend account
Go to resend.com → Sign up. Resend has a free tier of 3,000 emails/month. No credit card required. It is the simplest email API available and has first-class Deno/Edge Function support.
2
Add and verify your sending domain
Go to Domains → Add Domain. Add vesto.finance (or your actual domain). Resend will give you DNS records to add — three TXT records and one MX record. Add them in your DNS provider (Cloudflare, Namecheap, etc.) and click Verify. This takes 5–30 minutes.
If you do not own vesto.finance yet, use onboarding@resend.dev as the from address for testing only. It works without domain verification but emails go to spam in production.
3
Get your API key
Go to API Keys → Create API Key. Name it vesto-edge-functions. Copy the key (starts with re_) and paste it into your Supabase Edge Function secrets as EMAIL_API_KEY.
09

Verify the wiring end to end

After completing all steps, run these five checks to confirm everything is connected.

✓
Check 1 — Supabase connection
Open the app in your browser. Open DevTools → Network tab. Filter by supabase. Perform any action that reads data (e.g. navigate to the Lender Marketplace). You should see requests going to https://YOUR_PROJECT_REF.supabase.co/rest/v1/... and returning 200 OK responses. If you see 401 errors, your anon key is wrong.
✓
Check 2 — RLS data isolation
Sign up as a seller. Submit an invoice. Sign out. Sign up as a different seller. Navigate to invoices. You should see zero invoices — the second seller cannot see the first seller's invoices. If you see the first seller's invoices, RLS is not working.
✓
Check 3 — Buyer acknowledgement email
Log in as admin at /admin. Find a pending invoice. Click Approve → set settlement terms → Confirm. The send-acknowledgement Edge Function should fire and send an email to the buyer's AP address. Check your Resend dashboard under Logs to confirm delivery.
✓
Check 4 — Wallet connection
Click "Connect Wallet" in the navbar. Connect MetaMask or any injected wallet. The wallet should connect to Arc Testnet. If it prompts to switch networks, accept. Once connected, your USDC balance should appear (it will be 0 if you haven't received testnet USDC yet).
✓
Check 5 — Admin portal separation
Navigate to the main app. Confirm there is no Admin option in the role switcher — only Seller and Lender. Then navigate directly to /admin. Confirm you see only the email + passcode gate with no admin content visible. Log in with a @vesto.finance email and passcode 123456. Confirm the full admin panel appears only after authentication.
10

The five exposure risks

These are the five mistakes that would give an attacker access to your data or your users' funds. Each one is explained plainly.

Risk 1 — Service role key in a VITE_ variable

If you add VITE_SUPABASE_SERVICE_ROLE_KEY to your .env or Netlify, Vite bundles it into the browser JavaScript. Anyone who opens DevTools → Sources can read it in plain text. With the service role key, an attacker can read, modify, or delete every row in your database — all invoices, all seller profiles, all lender positions, all KYC documents.

Current status: Clean. The grep across all src/ files confirms zero references to SERVICE_ROLE with a VITE_ prefix.

Risk 2 — Committing .env to GitHub

Even if you fix it immediately, git history is permanent. Anyone who ever had access to your repository can read the old commit and find your keys. GitHub's secret scanning will flag it, but the key is already compromised the moment it is pushed.

Current status: Clean. .env and all variants are in .gitignore. If this ever happens: rotate both keys immediately from the Supabase dashboard, then do a git filter-branch or BFG Repo Cleaner to remove the commit from history.

Risk 3 — RLS disabled on any table

With RLS disabled, any authenticated user — any seller, any lender — can run a query like SELECT * FROM invoices and get every invoice in the database, including funded amounts, lender IDs, and buyer details. With the anon key (which is public), even unauthenticated users could read everything.

Current status: All migrations include ENABLE ROW LEVEL SECURITY. Verify in Supabase dashboard after running migrations.

Risk 4 — Trusting user-supplied IDs

If your API or Edge Function accepts sellerId from the request body and uses it directly to query the database, any authenticated user can supply a different seller's UUID and read or modify their data. The session JWT, not the request body, must be the source of identity.

Current status: Fixed by the security hardening migration. All sensitive column updates use auth.uid() from the JWT, enforced by database triggers.

Risk 5 — Logging secrets in console.log

A console.log(apiKey) in an Edge Function writes the key to Supabase's log stream, which is visible in the Supabase dashboard and potentially in log aggregation services. A console.log(token) in the browser writes it to DevTools, which can be read by browser extensions.

Current status: Clean. Zero console.log calls found across all src/ and supabase/functions/ files.

When something breaks

Start with the Supabase logs. Go to Edge Functions → your function → Logs. Every invocation is logged with the request and response. Most issues are either a missing secret (the function logs "SECRET_NAME is not set") or an RLS policy blocking a query (the Postgres logs show "new row violates row-level security policy").

For wallet connection issues, check the Arc Testnet RPC in your browser's Network tab. For USDC balance not showing, confirm the wallet is connected to Arc Testnet (chain ID 9001 for Arc Testnet) and not a different network.
